# Agent Note: 院校录取的选科过滤在 SQL 中执行，且先于结果窗口

Status: implemented

[English](2026-09-28-college-admission-subject-filter.md) | 中文

## Problem

`/api/college-admission` 必须只返回考生所选科目能报的条目：要求了考生未选科目的条目不适用。两个缺陷让这条保证形同虚设。

选科要求列是 `bit(1)`，PyMySQL 返回 `b'\x00'`/`b'\x01'`。过滤用 `== 1` 与之比较，对两种取值都为假，因此从未剔除任何条目——查询"历史,政治,地理"却返回了北京大学理科试验班类，其要求是"物理,化学"。另一个独立缺陷是过滤发生在 `SELECT … ORDER BY admission_score DESC LIMIT 200` 之后，因此即便比较正确，被判断的那 200 行也是在未考虑考生选科的情况下选出的：安徽 2025 中按多科规则符合"物理,化学"的条目有 19277 条，而这个窗口只落进 168 条。

## Decision

`college_admission` 把要求写进查询。内存过滤被删除，7 个标志列也不再回读——条件下推后没有任何消费者，因此 `SELECT` 只保留展示字段 `subject_requirement`。NULL 与 0 都表示"无要求"，而 bit 比较留在 SQL 侧，在那里按数值求值。

查询追加什么条件，取决于请求声明了几个科目：

- **多个科目**——入参是完整组合，因此请求中未出现的科目意为考生没选它：每个未列出的列都加上 `(subject_x IS NULL OR subject_x = 0)`。
- **单个科目**——入参只声明一科、对其余科目未作说明，因此未出现的科目是**未知**而非"没选"：当被点名的列为"要求"（`subject_x = 1`）**或**该条不要求任何科目（7 列全为 NULL 或 0）时保留该条。

两种情形下响应都是"满足条件中分数最高的条目"，`LIMIT 200` 仍是硬上限。

响应按数据库原值返回：列上没有值就是 `null`，既不是 `0` 也不是空串。这些端点背后的可空列——`admission_score`、`admission_rank`、`enrollment_plan`、控制线的四个位次列、`fill_count`、`subject_mode`、`fill_mode`——都让"没有这个值"保持可见，因为 0 是真实的分数、位次或计划数。查询工具在其输出 schema 中声明了这一点：可能缺失的字段允许 null，因为工具注册表会用各自的 schema 校验每一个输出值，未声明的 null 会让这次调用失败。它们的渲染器点明缺失而不是替换成一个值——未公布位次的控制线打印"位次未公布"，模式缺失的填报规则打印"未公布"，而不是假定成另一种模式。

空 `subject`（端点接受它）不再是"返回全部"：它排除所有要求了任一科目的条目，只留下不要求任何科目的条目。

## Alternatives considered

**把单科当作完整组合**（像多科规则那样把其余六列约束为 NULL 或 0）。这是曾短暂发布的实现，也是"考生所选科目"这一读法自然给出的结果。它被否决，因为单科请求只陈述了一件事：只写"物理"的调用者并没有说考生没选化学，因此丢掉"物理,化学"的条目是在回答没人问的问题，在安徽 2025 上它会藏起提及物理的 19855 条中的 19389 条。

**把缺失值渲染为 `0` 与空串**（此前行为）。0 在这些列上都是真实取值——分数、位次、招生计划——因此未记录分数传给模型的是 `0`，读起来是最差结果而不是"没有数据"；空串同样与"记录了一个空备注"无法区分。选择放宽输出 schema，而不是把数据抹平。

**只修 Python 侧的比较**（例如 `value not in (None, 0, b'\x00')`）。它能让过滤真正生效，但窗口缺陷仍在：那 200 行依旧先于过滤被选出，因此"物理,化学"的查询只会答出 675 分以上恰好落在窗口内的约 168 条，另外约 19000 条被藏起来。

**放宽或去掉 `LIMIT`，再在内存里过滤。** 这会在每次请求时把整个匹配集读进服务进程——今天单个省-年就有 26278 行，并随数据增长——而且分页语义依然错误。

**用 `subject_x <> 1`（或 `NOT subject_x = 1`）作为 SQL 条件。** 更短，但三值逻辑把语义反转：列值为 NULL 时比较结果是 NULL，该行不会被返回，于是所有以 NULL 记录"无要求"的条目都会消失。"不限"这一情形必须显式命名。

**解析 `subject_requirement`（varchar）而不是标志列。** 该文本是展示字段（`物理,化学`），没有固定文法；而标志列是同一事实的机器可读表达。

## Consequences

回答现在随考生选科变化，且单科规则刻意是两者中更宽松的那个。安徽 2025 中"物理"匹配 19855 条，"物理,化学,生物"匹配 19665 条，"历史,政治,地理"匹配 6418 条，"技术"匹配 0 条。更宽松也意味着：同时要求物理与化学的条目会返回给只写了"物理"的调用者——其对立面（把未提及的科目当作没选）正是多科规则所做的事，并已按上述理由被否决。

在数据中存在"不要求任何科目"条目的省份，单科规则会让它们浮现：河南 2025 有 15399 条此类条目，而在那里"物理"请求最先返回的正是它们。

安徽 2025"地理"回答中那一条未记录分数的条目（阜阳师范大学 地理科学，定向西藏计划）现在以 `admission_score: null` 返回而非 `0`，其位次同理。

过去被窗口藏起来的条目重新可见。`LIMIT 200` 未变，匹配集超过 200 条时仍然无法从响应看出还有更多；分页不属于本次改动。

## Testing

本仓库没有针对该 Python 服务的自动化测试设施，因此改动是通过运行中的服务对真实数据库验证的。对"物理"/"历史"/"地理"/"政治"/"技术"/"物理,化学,生物"/"历史,政治,地理"/"物理,历史"，把端点返回的条目集合与一条独立编写的过滤查询算出的集合逐一比对，八组全部完全一致；它们各自是在 19855、6460、184、299、0、19665、6418、10973 条的匹配集上返回 200 行的窗口结果。

方向性检查确认了意图：同时要求物理与化学的最高分条目出现在"物理"的回答中，而要求化学但不要求物理的最高分条目没有出现。河南 2025 上，单科"物理"返回的前 40 行被回查数据库，全部不要求任何科目。空 `subject` 返回 0，不支持的科目名仍然 400。改动前，同样对"历史,政治,地理"的比对只与正确集合重合 4/81 行。

缺失值在同一条路径上做了验证。安徽 2025"地理"的回答恰好有一行分数为 `null`、没有一行是 `0`，与同一过滤条件下数据库的计数一致；工具也接受这样的值：对含 null 的条目，其输出 schema 报告零违规，而此前的 integer-only schema 报告 `must be an integer`，其渲染器把这些单元格打印为空。改动之前的验证需要归一化分数，因为 `None` 与 `0` 表示同一行；改动之后，它们是两个不同的事实。

其余端点用同样方式验证。西藏 2025 的四条控制线均未公布位次，现在返回 `rank: null`（此前是 `0`），而北京 2025 仍返回它记录在案的位次；新疆 2027 返回 `fill_count: null`，其工具 schema 现在允许该值。四个工具的 schema 都接受携带 null 的样例值，渲染器打印缺失（位次未公布 / 未公布）而不是替换成一个值。

## Deferred

`/api/college-admission` 的分页：上限是常量 200，既无法请求下一个窗口，也无法获知匹配总数。
