# Agent Note: AI 多元升学路径（草稿）

Status: proposed

[English](2026-09-29-multi-pathway-admission.md) | 中文

## 问题

v1.1 这条线要在既有高考数据包之上做 AI 引导的多元升学路径，而范围尚未固定。有一件事已经确定，因为今天实测过：一个改动可以落在错误的组合层里，却看起来像是成功了。

宿主服务（数据 API、会话级能力）通过 profile 的 bundle 加 patch 栈挂载，`dsh web --patch <file>` 在其上叠一个机器本地层。面向模型的能力（工具、命令、skill）属于 agent preset（`packages/preset/agent-presets/presets/cordis/agent.cordis.yml`）。两者是不同的树：覆盖层里写一个 agent preset 的条目，启动时会被拒 —— `patch: entry "tool-gaokao-query" not found`。反过来，写在错误层里的改动则安静地启动、什么也不改变。

## 提议

- **在独立实例上开发。** 3080 保持稳定实例、不带覆盖层。3081 以机器本地覆盖层（`cordis.3081.patch.yml`，已 gitignore）运行并开启 HMR，使客户端插件产物无需重新构建、重启或更换访问 token 就能到达浏览器。
- **禁用而不是删除。** 既有院校录取工具在 v1.1 的 agent 组合里被禁用，作为占位；它调用的 FastAPI 服务与数据链路保持原样，其他 preset 与仓库历史仍能用到。
- **每个新部件都按层归位。** 数据与服务走 profile 的 bundle 加 patch 栈；任何模型调用的东西进入 agent preset。一个改动如果说不清自己落在哪一层，就还没到能动手的状态。
- **先定框架再排功能。** 下面四个问题决定数据模型与工具面，因此在实现排期之前先回答：做哪些路径（强基计划 / 综合评价 / 专项计划 / 中外合办 / 港澳与留学 / 志愿填报本身）、主要产出是什么（咨询式对话、排序推荐、还是表单驱动的报告）、数据从哪来（扩展现有 MySQL 表结构与 FastAPI 服务，还是在其旁新增服务）、以及新能力是替换 preset 里的录取工具还是与它们并存。

## 考虑过的替代方案

**直接删除录取工具与 gaokao-api 包。** 这会切断其他 preset 与历史复查可用的数据链路，并把"v1.1 不做"表达成"仓库不做"。禁用才是诚实的形态；删除是另一个决策。

**用 `--patch` 覆盖层配置 agent 层。** 实测不可行：因为条目不在 profile 树里，覆盖层会被拒。记录为已知约束，而不是一个选项。

**直接在 3080 上开发。** 会把试验开关与 HMR 监听带进日常使用的实例，而且每次重启都会让访问 token 失效、打断正在进行的会话。

**先把数据源做大（扩表或新库），再定产品形态。** 表结构由路径集合决定，而路径集合尚未定；先扩表等于把猜测冻进 schema。

## 验收标准

- v1.1 的 agent 组合里不再注册任何录取查询工具，而其他 preset 仍然保有它们。
- FastAPI 服务仍能独立启动与调用；它的路径与配置未变。
- 3081 实例能用 `cordis.3081.patch.yml` 组合出宿主层条目，用 `pnpm dsh web --patch ./cordis.3081.patch.yml --dump-config` 只读验证。
- 本记录只在上面四个框架问题都留下明确答案之后，才从 `proposed` 推进到 `implemented`。

## 风险

- **层级错配（最高）。** 内容正确、层级错误，启动无报错却毫无效果 —— 正是本记录开头记下的失败。
- **低估数据成本。** 录取数据在公网 RDS 上、每请求新建连接（实测约 250 ms/次）。新的路径功能若沿用同一模式，会把这份延迟带进交互链路。
- **产出形态未定导致工具面反复。** 对话、排序推荐、报告三者对应不同工具；在选定之前动手会返工。
- **范围蔓延。** 路径集合一直不定，实现就会被"再加一个路径"不断推翻。
